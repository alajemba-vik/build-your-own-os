Interruptions et plantages

Pour l’instant, si votre code fait une erreur, le PC redémarre sans rien dire. Vous apprenez au processeur où aller quand quelque chose se produit, et vous obtenez un vrai écran rouge de kernel panic qui dit ce qui s’est mal passé.

L’idée

  • Une interruption fait lâcher au processeur ce qu’il fait pour exécuter un gestionnaire (handler), puis y revenir. Certaines viennent du processeur lui-même quand le code se trompe (les exceptions : division par zéro, instruction invalide, défaut de page… numéros 0 à 31). D’autres viennent du matériel, comme le clavier (chapitre 4).
  • L’IDT (Interrupt Descriptor Table) est une liste de 256 adresses de gestionnaires. On la charge avec l’instruction lidt.
  • Avant cela, le processeur veut une GDT (Global Descriptor Table) : les anciennes puces x86 découpaient la mémoire en segments. Nous créons deux segments qui couvrent tous les deux les 4 Gio (code en 0x08, données en 0x10), et nous n’y pensons plus jamais.
  • Les gestionnaires commencent en assembleur (des stubs) : ils sauvegardent tous les registres, appellent une fonction C avec un pointeur vers eux, puis restaurent tout et exécutent iret. Certaines exceptions empilent un code d’erreur et d’autres non ; les stubs empilent un faux 0 pour que toutes les interruptions se ressemblent.
  • Si un plantage survient pendant le traitement d’un plantage, le processeur abandonne : c’est une triple faute (triple fault). QEMU s’arrête (nous utilisons -no-reboot).

À vous

  1. GDT, IDT et écran de panique

    Chapitre 3. Ajoute une GDT plate avec trois entrées (nulle, code noyau 0x08, données noyau 0x10, couvrant toutes deux 4 Gio) dans src/gdt.c, chargée par une fonction assembleur gdt_flush dans src/cpu.S qui recharge tous les registres de segment et fait un saut lointain (far jump) pour recharger CS.

    Puis une IDT dans src/idt.c avec 48 entrées qui pointent vers des stubs assembleur isr0..isr47 dans cpu.S. Chaque stub empile un faux code d’erreur 0 quand le processeur n’en empile pas (il en empile un pour 8, 10-14, 17, 21, 29, 30), empile son numéro, et saute vers un stub commun qui sauvegarde tous les registres (pushal et les registres de segment), charge le segment de données du noyau et appelle isr_handler(struct regs *r) en C. Mets une table des 48 adresses de stubs dans cpu.S. Définis struct regs dans src/cpu.h, exactement dans l’ordre où les valeurs sont sur la pile.

    Reprogramme aussi le PIC pour que les IRQ matérielles 0-15 utilisent les interruptions 32-47, mais garde-les toutes masquées pour l’instant.

    Pour les exceptions 0-31, affiche un écran rouge KERNEL PANIC avec le nom de l’exception, le code d’erreur, eip et les registres, puis arrête le processeur pour toujours. Dans kernel_main, affiche des lignes « [ OK ] » après chaque étape.

    make run

  2. Faites-le planter exprès

    Ajoute un test temporaire à la fin de kernel_main qui exécute l’instruction ud2 (assembleur en ligne), pour que je voie l’écran de panique. Explique ce que veut dire « Invalid opcode ».

    Vous devez voir l’écran rouge avec Invalid opcode. Essayez ensuite une division par zéro (demandez à l’IA comment en écrire une que le compilateur ne supprime pas), puis supprimez le test.

  3. Comprenez-le

    Demandez à votre IA : Qu’est-ce que le processeur empile exactement quand une interruption arrive ? Pourquoi struct regs doit-elle correspondre exactement à ce qu’empile le stub ? Qu’est-ce que iret ? Pourquoi faut-il reprogrammer le PIC ?

Ça marche quand

  • Le démarrage affiche [ OK ] GDT et [ OK ] IDT.
  • ud2 donne un écran de panique rouge avec « Invalid opcode », et QEMU reste ouvert.

QEMU se ferme dès qu’il démarre : c’est une triple faute. Lancez ceci et collez-en la fin à votre IA : on y voit les dernières interruptions et pourquoi le processeur a redémarré :

qemu-system-i386 -kernel build/kernel.elf -no-reboot -d int,cpu_reset 2>&1 | tail -40

Les causes habituelles : un stub avec le mauvais réglage de code d’erreur, struct regs dans le mauvais ordre, un __attribute__((packed)) oublié sur les structures des tables, ou le saut lointain dans gdt_flush.
