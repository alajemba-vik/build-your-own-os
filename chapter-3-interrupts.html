Interrupts and crashes

Right now, if your code does something wrong, the PC silently restarts. You teach the CPU where to go when something happens, and you get a proper red kernel panic screen that says what went wrong.

The idea

  • An interrupt makes the CPU drop what it's doing and run a handler, then come back. Some come from the CPU itself when code goes wrong (exceptions: division by zero, invalid instruction, page fault… numbers 0 to 31). Others come from hardware like the keyboard (chapter 4).
  • The IDT (Interrupt Descriptor Table) is a list of 256 handler addresses. We load it with the lidt instruction.
  • Before that, the CPU wants a GDT (Global Descriptor Table): old x86 chips cut memory into segments. We make two segments that both cover all 4 GiB (code at 0x08, data at 0x10), and then never think about them again.
  • Handlers start in assembly (stubs): they save every register, call one C function with a pointer to them, then restore everything and run iret. Some exceptions push an error code and some don't; the stubs push a fake 0 so every interrupt looks the same.
  • If a crash happens while handling a crash, the CPU gives up: a triple fault. QEMU stops (we use -no-reboot).

Do it

  1. GDT, IDT and the panic screen

    Chapter 3. Add a flat GDT with three entries (null, kernel code 0x08, kernel data 0x10, both covering 4 GiB) in src/gdt.c, loaded by an assembly function gdt_flush in src/cpu.S that reloads all segment registers and does a far jump to reload CS.

    Then an IDT in src/idt.c with 48 entries pointing to assembly stubs isr0..isr47 in cpu.S. Each stub pushes a fake error code 0 when the CPU doesn't push one (the CPU pushes one for 8, 10-14, 17, 21, 29, 30), pushes its number, and jumps to a common stub that saves all registers (pushal and the segment registers), loads the kernel data segment, and calls isr_handler(struct regs *r) in C. Put a table of the 48 stub addresses in cpu.S. Define struct regs in src/cpu.h in the exact order things are on the stack.

    Also remap the PIC so hardware IRQs 0-15 use interrupts 32-47, but keep them all masked for now.

    For exceptions 0-31, show a red KERNEL PANIC screen with the exception's name, the error code, eip and the registers, then stop the CPU forever. In kernel_main, print "[ OK ]" lines after each step.

    make run

  2. Crash it on purpose

    Add a temporary test at the end of kernel_main that runs the ud2 instruction (inline assembly), so I can see the panic screen. Explain what "Invalid opcode" means.

    You should see the red screen with Invalid opcode. Then try a division by zero (ask the AI how to make one the compiler doesn't remove), then delete the test.

  3. Understand it

    Ask your AI: What exactly does the CPU push on the stack when an interrupt happens? Why must struct regs match the stub's pushes exactly? What is iret? Why does the PIC need to be remapped?

It works when

  • The boot shows [ OK ] GDT and [ OK ] IDT.
  • ud2 gives a red panic screen with "Invalid opcode" and QEMU stays open.

QEMU closes as soon as it starts: a triple fault. Run this and paste the end of it to your AI, it shows the last interrupts and why the CPU reset:

qemu-system-i386 -kernel build/kernel.elf -no-reboot -d int,cpu_reset 2>&1 | tail -40

The usual causes: a stub with the wrong error-code setting, struct regs in the wrong order, a missing __attribute__((packed)) on the table structs, or the far jump in gdt_flush.
